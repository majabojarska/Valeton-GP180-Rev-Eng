# Valeton GP180 Reverse Engineering
## Goals
- Reverse engineer the SysEx protocol of the Valeton GP180 guitar multi-effects processor.
- Build a platform-agnostic web application (PWA), to manage presets, firmware updates, IR/NAM loading, and settings for the GP180. The application will leverage the [WebMIDI API](https://developer.mozilla.org/en-US/docs/Web/API/Web_MIDI_API) to communicate with the device over MIDI.
## Non-goals
- Modification of the GP180 firmware or hardware, although hardware extension modules may be considered in the future.

Nice project. I pulled some quick context to ground the plan — worth knowing before you start:

    The GP5/GP50 web app (drewmerc302/valeton-gp50) already exists as a live reference: browser-based, WebMIDI, reverse-engineered SysEx, no vendor SDK, presets/blocks/models all working. If GP150/GP180 share a protocol lineage with GP50, this could save you weeks.
    Valeton's own support answer on the forum: GP-200 presets are explicitly NOT compatible with GP50/150/180 — so that open question is settled negatively; treat GP200/gp200editor as architecturally useful but not byte-for-byte reusable.
    The most directly useful prior art for your methodology isn't the GP200 gist so much as the gp200editor / toneforge project (phash / hede0n): they reverse-engineered a 14-message-type SysEx protocol and a 1224-byte .prst format (magic TSRP, 11 blocks × 72 bytes, uint32 effect code + active flag + 15×float32 params) using Wireshark + USBPcap + a Python capture GUI, cross-checked against Valeton's own algorithm.xml effect definitions pulled from their desktop software. That capture-tool + GUI pattern is exactly what you should replicate for the GP180.

Phased plan

Phase 0 — Instrumentation before anything else

    Get a GP180 on a workbench with USB passthrough capture: Wireshark + USBPcap (Windows) or usbmon (Linux) sitting between the pedal and Valeton Suite v2.1.0.
    Build (or fork) a small capture-to-JSON tool that timestamps and dumps every SysEx blob (F0…F7) separately from other USB traffic — this becomes your ground-truth corpus. Store raw captures in a repo captures/ folder with a short description per file (what UI action triggered it).

Phase 1 — Elicit a labeled corpus from Valeton Suite

    Systematically drive every UI action in Valeton Suite v2.1.0 (connect/handshake, read single preset, read all presets, write preset, rename, reorder, param tweak, firmware version query, IR upload, NAM upload, settings change) one at a time, capturing before/after diffs.
    Also capture the firmware update flow separately — it's likely a distinct bulk-transfer protocol (possibly DFU-like framing inside SysEx), worth isolating early since it's higher-risk (bricking) and needs the most caution.
    Do the same for v2.0.3 to see whether NAM A2 lite support changed the message set — diffing v2.0.3 vs v2.1.0 traffic tells you which message types are new.

Phase 2 — Static analysis to accelerate decoding

    Load both firmware images and both Suite builds (Win/Mac if useful) into Ghidra. Look specifically for: SysEx header constants (manufacturer ID, device ID bytes you'll see repeat in every capture), a command dispatch table/switch statement, and CRC/checksum routines (very common in Valeton-style protocols — the GP200 work found a magic string TSRP reversed from PRST, so expect similarly "reversed ASCII" quirks).
    Cross-reference constants found in the binary against bytes you already see in captures — this is much faster than pure black-box guessing, and is how you'll figure out framing (length fields, sequence numbers, ACK/NAK message types) rather than just payload contents.

Phase 3 — Compare against GP5/GP50 protocol

    Pull the GP5/GP50 SysEx docs/code from drewmerc302's repo and diff its message structure (header bytes, command IDs, chunking scheme) against your GP180 captures. Given "HD Modeling Tech II" and NAM support are new to GP150/GP180 (per the forum thread), expect the framing/transport layer (handshake, chunked reads, checksums) to be shared with GP50, while the preset payload (block/model/param encoding) is likely closer to GP200's structure given both do NAM+IR. Test this hypothesis early — it determines how much of the GP50 code you can reuse vs. how much preset-format work is closer to gp200editor's approach.

Phase 4 — Document and codify

    Write the protocol spec as you go (message types, byte layout, checksums, chunking/handshake state machine) in a living markdown doc in the repo, mirroring the level of detail gp200editor reached (message type table + byte-level preset layout). Build a small Python or Node SysEx parser/encoder library before touching the browser — it's much faster to iterate against captured .syx files than live hardware, and it becomes the source of truth your PWA's TS code ports from.

Phase 5 — PWA implementation

    Use gp200-studio and the GP50 web app as UX/architecture references (single-page WebMIDI app, no backend, live device sync).
    Build incrementally in this order: connect/handshake → read presets (read-only browser) → preset editing/write-back → reorder/rename → IR loading → NAM loading → firmware update (last, and behind extra confirmation UI given the brick risk).
    Keep the protocol layer as an isolated TS module (mirrors your Python reference parser) so you can unit-test it against your captured .syx corpus without hardware in CI.

Phase 6 — Validate safely

    For anything that writes to the device (presets, settings, and especially firmware), validate round-trip on read-only operations extensively first, and add a "dry run" mode that decodes/encodes without sending. Firmware update in particular deserves its own isolated test pass with a way to recover (check whether Valeton Suite has a documented recovery/DFU mode you can fall back to if a custom update attempt fails).

Good specific question — Ghidra's value here splits sharply between the two binary types you listed, so worth treating them differently.
Firmware (GP180 v1.0.0 / v1.1.1) — Ghidra's real sweet spot

This is where Ghidra does the heavy lifting, since you can't easily instrument the MCU dynamically.

    Identify the target before importing. Unzip the firmware and check for a header/bootloader signature to determine architecture (almost certainly ARM Cortex-M, given the class of DSP/MCU used in modeling pedals) and whether it's a raw binary or has a container format (some Valeton firmware updates wrap the actual image in a proprietary header — check for a bootloader magic string or CRC header before the real code starts). Use binwalk first to spot embedded filesystems/compressed blobs before touching Ghidra.
    Getting the load address right matters more than usual. Raw ARM firmware imported at the wrong base address will produce garbage disassembly. Look for a vector table at offset 0 (initial stack pointer + reset vector — both will look like plausible pointers into the image) to infer the real base address, then re-import with that base set.
    Find the SysEx entry point via strings and constants, not by reading the whole binary. Search Ghidra's Defined Strings / Memory Search for:
        The bytes F0 F7 or your MIDI manufacturer ID (once you know it from a capture) as a byte pattern — this is the fastest way to jump straight to SysEx parsing code, since the parser almost certainly checks for 0xF0 as a leading byte.
        Any embedded strings like "SysEx", "MIDI", "PRST", "NAM", "IR", error strings — firmware often has debug/error strings baked in even in release builds.
    Once you're in the parser, use the decompiler and work outward. Identify the dispatch (usually a switch/jump table keyed on a command byte) — each case is one of your ~14-ish message types. Rename functions as you identify them (handle_preset_read, handle_fw_update_chunk, etc.) so cross-references stay legible.
    Diff the two firmware versions. Ghidra's Version Tracking tool (or exporting both to BinDiff if you have it) will show you exactly what changed between v1.0.0 and v1.1.1 — since v1.1.1 is "compatible with computer software v2.1.0" (NAM A2 lite), diffing should point you straight at the new/changed SysEx handlers for NAM loading, which is one of your PWA's harder features.
    Checksum/CRC routines are worth isolating early — find them via their characteristic loop-with-XOR/shift-and-polynomial pattern, since you'll need to replicate them exactly in your JS/TS encoder or the pedal will silently reject writes.

Valeton Suite (desktop software)

Check this first before assuming Ghidra is even the right tool: unzip the installer and look at what's actually in it. If it's Electron (an app.asar, resources/app folder, Electron.exe/node binaries), Ghidra is the wrong tool — you'd instead unpack app.asar and read the JS/TS source more or less directly (much faster than decompiling). If it's Qt/native C++ (a .dll/.so/.dylib doing the actual MIDI I/O, likely linking something like RtMidi or a raw platform MIDI API), then Ghidra is the right call:

    Import the main executable and any plugin/DLLs that reference MIDI (check imports for winmm.dll on Windows or CoreMIDI symbols on Mac — that tells you which module owns device I/O).
    Same string/byte-pattern search strategy as firmware: look for the manufacturer ID bytes, "F0"/"SysEx" literals, or the reversed-ASCII magic strings (recall GP200's .prst used TSRP = reversed PRST) since Valeton's tooling seems to like that pattern.
    The Suite side often mirrors the firmware's message construction almost 1:1 (build packet → checksum → send), so you can frequently confirm a hypothesis from firmware analysis by finding the matching encoder function in the Suite binary — cross-validating two independently-compiled implementations of the same protocol is a strong sanity check.
    If it does turn out to be Electron, the equivalent "aha" moment comes from grep-ing the unpacked JS for sendSysex/0xF0/hex arrays rather than decompiler work — worth checking this first since it could save you the whole binary-analysis phase for the Suite side entirely.

One practical note: whichever binary type the Suite turns out to be, do that identification step before your Phase 2 static-analysis work in the plan above — it changes your tooling (Ghidra vs. asar unpack) enough that it's worth confirming early rather than assuming.
